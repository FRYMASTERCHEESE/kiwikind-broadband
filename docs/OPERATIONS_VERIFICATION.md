# Prelaunch operations verification

Keep intake and admin disabled throughout. These are procedures, not completed evidence. Do not reset real accounts, export customer records into CI, or restore over production.

## Recovery drill for the PostgreSQL deployment

1. Confirm the dedicated database identity, backup owner, encrypted storage destination, access policy and approved retention. Keep credentials in the secret manager; never put them in command arguments, reports or repository files.
2. Use the provider's supported consistent snapshot or a compatible `pg_dump` custom-format backup, with connection credentials supplied securely through PostgreSQL environment/service configuration. Encrypt any off-host copy and verify the job's completion and restore access. A successful deployment is not a backup.
3. Restore only into a new, isolated staging database. Restrict operator access because restored data remains personal data. Disable email delivery, intake, admin and all external side effects. Never point CI at this database.
4. Check migration state and aggregate counts for users, Google identities, orders, tickets, messages, invoices and privacy requests. Check ownership relationships without copying personal fields into logs. Use a designated synthetic account for export and account-isolation checks.
5. In the isolated restored database, invalidate restored sessions with `python manage.py shell -c "from django.contrib.sessions.models import Session; Session.objects.all().delete()"`. Verify a fresh login with the synthetic staging account. Do not delete production sessions as part of a drill.
6. Record backup timestamp, restore timestamp, source/destination identifiers, aggregate comparison results, operator and failures. Measure actual recovery point/time against the proposed 24-hour/one-business-day targets. Resolve failures before calling the drill passed. Dispose of the staging copy under the approved retention policy.
7. Schedule recurring backup verification and restore drills through the approved provider. This repository does not attest that a schedule exists. SQLite instructions in DEPLOYMENT.md apply only to SQLite, not this PostgreSQL deployment.

## Email delivery verification

1. Confirm approved sender/domain and SMTP configuration in the secret manager. Use an authorized synthetic mailbox and isolated staging origin with the same sender infrastructure. Keep public intake closed.
2. Exercise registration only in staging: verify message delivery, correct HTTPS origin, expiry and single-use rejection. Test the existing password-reset flow for a synthetic password account, including one successful reset, reuse rejection and rejection of the old password.
3. Verify an existing authenticated session for that account is rejected after password reset. Confirm the new password signs in and other synthetic users cannot see its records. Do not change an owner's working Google sign-in or ask them to repeat a successful phone test.
4. Record timestamps, delivery outcome, sender authentication results from received headers and link results without recording reset tokens, passwords or mailbox contents. Check provider bounces/failures with the responsible operator.
5. Local-memory test email and accepted SMTP submission are not proof of mailbox delivery. Mark this gate complete only after actual receipt and flow evidence exists.

## Deployment check

Require backend SQLite and PostgreSQL tests, website regressions and the existing Android checks before merging. Confirm the deployed commit, `/healthz`, `/api/status` (intake false, billing false, live services false), `/api/me` anonymous 401, `/admin/` disabled and API cache control. Preserve existing accounts and permanent signing identity. No signing keys are generated by this procedure.
